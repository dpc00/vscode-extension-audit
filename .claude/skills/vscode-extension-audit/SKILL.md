- The MCP tools may not be in the harness's tool list after a restart. In opencode, reconnect without editing a file and without restarting the harness: `opencode api post '/api/experimental/mcp/vscode-mcp/connect?location%5Bdirectory%5D=<cwd>'` (the route is location-scoped; a wrong cwd answers McpServerNotFound). This is required when a restart brings NEW tools - opencode keeps the tool list it first fetched, so a tool the server already serves still answers "Unknown tool" (2026-11-12: `self_test` was unknown while 0.8.4 was live). A reload to the same tool set needs nothing: poll `get_help` until `pid` changes, then work. Prefer the tools or this route over hand-posting JSON-RPC to `http://127.0.0.1:9560/mcp`.

## Rules (Donald)

1. **One extension at a time, tested for real.** Use every documented feature on realistic input and compare exact output with what the documentation promises. Starting an extension (activation, a startup log) proves nothing and is never a result. He has twice thrown away work that was only startup checks or static scans: do not rebuild a bulk smoke-test pipeline.
2. **Work through vscode-mcp.** A step it cannot do is a gap in vscode-mcp: write it in the baton and in `vscode-mcp\README.md`, and fix the tool when it is cheap (0.4.0 added `batch`, `complete`, `hover`, `definitions`, `insert_text` that way).
3. **Installs:** only extensions, only in the portable VS Code, only through `install_extension`. No admin, nothing outside `vscode_portable`. Write the ledger line BEFORE each install; after each test uninstall, reload, verify `list_extensions` is clean, write the removal line. No Windows Sandbox, no VM, no background tasks, no monitors, no scheduled jobs (his orders 2026-10-28).
4. **Safety first (PROCEDURE.md):** triage without running, then live test. An extension that needs an account, a paid licence, a cloud service or admin rights: skip it and record nothing (RESULTS.tsv has only extensions that were tested).
5. **Reporting (his go, 2026-10-28: "find all the bugs and post issues"):** search the upstream issues first (several phrasings, `gh search issues --repo OWNER/REPO "words" --json number,title,state`), skip archived repos and deprecated extensions, one issue per distinct defect, body starting "Claude reports (found while ...)" with versions, minimal repro, actual and expected, cause. Link in the row. **No pull requests and no forks.**
6. **Do not mistake a test artifact for a defect.** Forcing activation with no editor open produced three false findings; a wrong cursor column or CRLF vs LF in a new file produced false failures. Reproduce a suspect result a second way and read the extension's code for the cause before reporting.
7. **Git in this repo:** ONE commit per day, which you amend after each piece of work (`git add -A; git commit --amend --no-edit; git push --force-with-lease origin main`). He asked for exactly this, public on GitHub. A new calendar day starts a new commit. `git add -A` and publish everything except real secrets and junk (`.gitignore` is minimal). No `Co-Authored-By` change needed on amend.
8. **No Bash tool.** Use Read, Grep, Glob, Edit, Write; PowerShell only for real commands, one tool call at a time when a permission prompt can appear. Deletes go to the Recycle Bin with `recycle.ps1`, one path per call.
9. **Check "already tested" before every extension:** `RESULTS.tsv` by exact id, case-insensitively.
10. **Say what you will do in one line and do it; do not ask questions he can answer by a rule above.** Reports are short: what was tested, what is wrong, the link.

## Testing techniques (vscode-mcp)

- A whole test in one `batch` call: `create_file`, `open_file` (with `line` and `character` to place the cursor), `{sleep: ms}`, `run_command`, `get_text`. Build the call list in PowerShell, `ConvertTo-Json -Depth 10 -Compress`, write to a file, post it. **The batch item key is `arguments`** (sublime-mcp's batch takes `args`; passing `args` here silently delivers empty arguments to every path-carrying tool, which crashes with `Cannot read properties of undefined (reading 'replace')` — cost a false "batch is broken" diagnosis on 2026-11-11).
- **`run_command`'s own argument key is `args`** (an array, spread into the command as separate arguments); `arguments` is only the key INSIDE a batch item. Getting it wrong is silent-ish: `args` missing gives `Cannot read properties of undefined (reading 'command')`, and passing an array where the command wants one object gives `(reading 'arguments')`. Extension-internal commands (ids starting `_`) often take a tree context object rather than plain arguments, e.g. Project Manager's `_projectManager.toggleProjectEnabled` needs `args: [{command: {arguments: [null, "Name"]}}]`.
- Polling after `reload_window` or any delayed effect: a `for` loop with no timer in a Code Mode program spins instantly and proves nothing (it kept answering from the OLD host and looked like "the reload did not happen"). Sleep inside a `batch` (`{sleep: 4000}`) or with the shell's `Start-Sleep`, then read.
- **Speed (vscode-mcp 0.6.x): one phase of a test = one `batch`, with no fixed sleeps, and the assertions inside it.** Write settings -> `wait_config` (the exact key and value) -> `open_file` -> `run_command` -> `wait_for` (the file the program writes, `contains` the marker) -> `expect` (pass/fail for the file the action changed, so the result needs no reading). `run_shell` runs a command in the workspace folder and returns exit code/stdout/stderr, so disk state and exit codes come back inside the batch; never open a terminal or a second PowerShell for it. Assert on a program's effects (files it writes, exit codes) instead of screenshotting the output channel, which cannot be read through the API.
- `expect` compares the open document (unsaved edits included) or the file on disk: `equals`, `contains`, `not_contains` or `matches` (regular expression, no `(?i)` - JS has no inline group; use `[Tt]`), line endings normalised. On failure it returns the first differing line with expected and actual, so only mismatches cost reading. Batch it after every action that changes text.
- An extension that serves HTTP is tested with curl or node through `run_shell`, no browser: status codes with `-w`, headers with `-D file`, and one node script can do HEAD/Range/If-None-Match in a single call. A websocket feature (live reload) is a client script run in the foreground that touches a file itself and collects the messages; extension packages often already ship a client module (`faye-websocket` in Live Server) - require it by absolute path.
- Put a marker character in test text to mark the cursor and compute line/column from it; compare the file text after the action with an expected string exactly, normalising line endings (new files in this editor are CRLF; only compare CRLF deliberately).
- Completions, snippets, hover, definition: `complete` (path, line, character, optional `filter`, `limit`), `hover`, `definitions`. `run_command vscode.executeCompletionItemProvider` is capped at 20,000 characters and a JS/TS file returns every global.
- Features triggered by typing (Enter indentation, comment generators such as `/**` + Enter): place the cursor with `open_file`, then `run_command type` with `[{"text": "\n"}]`. Extension commands bound to a key (such as `pythonIndent.newlineAndIndent`) can be run directly.
- Snippet bodies: `editor.action.insertSnippet` with `[{"snippet": "..."}]` or `{"name": "...", "langId": "..."}`.
- Diagnostics: `get_diagnostics` (optionally `source`). Another extension's output or log: `read_log` (pattern). Formatting and transform commands: `run_command` then `get_text`.
- JSON bodies with non-ASCII characters: escape them as `\uXXXX` before posting (Windows PowerShell 5.1 writes the console codepage otherwise). PowerShell 5.1 has no `` `u{e9} `` escape: use `[char]0xE9`.
- Not readable at all: inline decorations, tree views, webviews (those need a screenshot tool, and are out of reach of the extension API).
- An extension pack installs its members too: triage the members and record a row for each.

- `run_command` and the generated command tools now answer in about 12 s with `pending: true` plus the native dialogs they can see when a command has not returned (vscode-mcp 0.8.3): a modal is the usual cause, and `dismiss_dialog` is then one call away. Answering it lets the command finish. Do not re-run the command blindly; check the effect first.
- **`editor.action.formatDocument` with more than one formatter registered for the language raises VS Code's native "Configure Default Formatter" dialog** (met with beautify + the built-in JS formatter, 2026-11-12; the user waited minutes on it). Pin the formatter in workspace settings FIRST - `"editor.defaultFormatter": "<extension id>"` - and the dialog never appears. If it does appear anyway, `list_dialogs` + `dismiss_dialog` immediately; never leave it up.

## Traps

- Settings a probe writes go to the WORKSPACE ROOT (`.vscode/settings.json` beside the folder `Code.exe` was started with), never inside a probe subfolder: a nested one is not read at all, `wait_config` burns its 10 s timeout, and the extension silently uses its defaults.
- `install_extension` goes through VS Code's own CLI; `workbench.extensions.installExtension` opens a "trust the publisher?" dialog that nothing can answer.
- `workbench.action.closeAllEditors` on a dirty tab raises VS Code's native Save dialog and blocks the workbench behind the call (seen 2026-11-11 in the Bookmarks round). Save, revert, or `close_file` with `discard: true` (0.4.2 reverts first) before closing in bulk; answering the dialog needs computer-use and the Escape lock then needs the API reconnect.
- A freshly installed extension appears in `list_extensions` only after `reload_window`; an uninstalled one stays listed until the same reload, and its folder is deleted at VS Code's next start (`data\extensions\.obsolete`). Uninstalling an extension that others depend on can fail.
- `reload_window` answers first and the server restarts; the OLD extension host keeps answering for 1-3 s, so a ready check that succeeds instantly is stale (it returned the pre-reload extension list and made a finished uninstall look unfinished). Poll `get_help` until `pid` changes: recovery is about 2-4 s. A failed call aborts an `execute` block, so retry as a new call.
- A test that stops and restarts a server needs ~1.2 s between the two: Live Server's StopServer waits 1000 ms internally and a start sent sooner is silently lost. Poll until the port refuses, then wait 1.2 s, then start.
- Extension ids come back with the publisher's own capitalisation; paths in results use a lower-case drive letter.
- The MCP server refuses requests with an `Origin` header and names other than localhost or an IP.
