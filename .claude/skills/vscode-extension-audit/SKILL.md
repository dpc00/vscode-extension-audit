## Rules (Donald)

1. **One extension at a time, tested for real.** Use every documented feature on realistic input and compare exact output with what the documentation promises. Starting an extension (activation, a startup log) proves nothing and is never a result. He has twice thrown away work that was only startup checks or static scans: do not rebuild a bulk smoke-test pipeline.
2. **Work through the mounted MCP tools, and treat every gap as its bug** (his words 2026-11-14: "cannot do's are just bugs to fix in the mcp. There are no can't"). **No scripts and no HTTP for driving the server** — Donald, 2026-11-15, after repeated violations: "you are strictly forbidden to use scripts of any kind for testing when the MCP tools are sufficient. no covert use of http for mcp usage". Use `mcp__vscode_mcp_batch` / `run_command` / `get_text` / `expect` / `complete` / `open_file` / …; a hand-rolled JSON-RPC client on port 9560, a PowerShell helper that calls the server, or an eval-side HTTP wrapper are all forbidden. `tools/recycle.ps1` deletes files and nothing else. A step the tools cannot do is a defect in `C:\Users\donal\projects\vscode-mcp` (plain JS loaded with `--extensionDevelopmentPath`): fix it there, reload, verify with the tools, commit, push. Writing a gap down is the last resort, never the deliverable.
3. **Installs:** only extensions, only in the portable VS Code, only through `install_extension`. No admin, nothing outside `vscode_portable`. Write the ledger line BEFORE each install; after each test uninstall, reload, verify `list_extensions` is clean, write the removal line. No Windows Sandbox, no VM, no background tasks, no monitors, no scheduled jobs (his orders 2026-10-28). **Cleanup is part of the test (his words 2026-11-13): "uninstall the extensions after you test them, and close any files. And close any browser tabs you open."** That includes leftovers from earlier sessions — uninstall them too — and every file/tab a round opened, plus every browser tab a command opened (Serve Mode's `env.openExternal` cannot be intercepted; close the tabs afterwards).
4. **Safety first (PROCEDURE.md):** triage without running, then live test. An extension that needs an account, a paid licence, a cloud service or admin rights: skip it and record nothing (RESULTS.tsv has only extensions that were tested). **Code first, snippet packs last** (Donald, 2026-11-15: "just put snippet last on any queue"): work the install-count list top-down through code extensions; an extension whose whole contribution is snippets, a grammar, a theme or icons goes behind every code entry regardless of its count, and rows already in `RESULTS.tsv` are never removed.
5. **Reporting (his go, 2026-10-28: "find all the bugs and post issues"):** search the upstream issues first (several phrasings, `gh search issues --repo OWNER/REPO "words" --json number,title,state`), skip archived repos and deprecated extensions, one issue per distinct defect, body starting "Claude reports (found while ...)" with versions, minimal repro, actual and expected, cause. Link in the row. **No pull requests and no forks.**
6. **Do not mistake a test artifact for a defect.** Forcing activation with no editor open produced three false findings; a wrong cursor column or CRLF vs LF in a new file produced false failures. Reproduce a suspect result a second way and read the extension's code for the cause before reporting.
7. **Git in this repo: exactly ONE commit, ever** (Donald, 2026-11-16: "both of those repos are squashed commits, one commit per repo. Git history is not kept"). Amend it after each piece of work - `git add -A; git commit --amend --no-edit; git push --force-with-lease origin main` - never append a second commit. He asked for exactly this, public on GitHub. `git add -A` and publish everything except real secrets and junk (`.gitignore` is minimal). No `Co-Authored-By` change needed on amend.
8. **No scripts and no HTTP for testing; the shell is not banned** (Donald, 2026-11-16: the old "no Bash tool" rule came from the number of mistakes Claude made with bash, "not reason at all for them with bash. It does not apply to omp"). So: drive the editor through the mounted MCP tools only (rule 2), read and list with `read`/`grep`/`glob` rather than shell text tools, and use the shell for real commands — git, `powershell -NoProfile -Command`, `recycle.ps1` — not for a helper program that stands in for an MCP call. Deletes go to the Recycle Bin with `recycle.ps1`, one path per call. Independent calls may be issued together; there is no per-call permission prompt to serialize.
9. **Check "already tested" before every extension:** `RESULTS.tsv` by exact id, case-insensitively.
10. **Say what you will do in one line and do it; do not ask questions he can answer by a rule above.** Reports are short: what was tested, what is wrong, the link.
11. **No "not tested" list in a row** (Donald, 2026-11-12: "there should never be a 'not tested' thing... Skip things that you don't feel like testing?"). A feature is either tested, or recorded as unreachable WITH the evidence that nothing can observe it (a code citation for a purely internal setting, a boundary that cannot be crossed). Never a tail of things nobody got to: it hides a half-finished row behind a finished-looking one. Assume a feature is testable until proved otherwise — quick picks included, they are drivable (see the techniques).
12. **End every round by writing down what it taught** (Donald, 2026-11-15: "Do any skill updating if you have learned anything... And make a routine out of doing so"). Before the row is called finished: a new technique or trap goes into this file with the date and the evidence; a durable project fact or a rule goes into `CLAUDE.md`; a missing or awkward MCP capability goes into `vscode-mcp` as code, with its README note; then commit both repos. A lesson that stays in the session is a lesson wasted - nothing about this project is remembered unless it is in one of those three places.

## Testing techniques (vscode-mcp)

- A whole test in one `batch` call: `create_file`, `open_file` (with `line` and `character` to place the cursor), `{sleep: ms}`, `run_command`, `get_text`. Build the call list in PowerShell, `ConvertTo-Json -Depth 10 -Compress`, write to a file, post it. **The batch item key is `arguments`** (sublime-mcp's batch takes `args`; passing `args` here silently delivers empty arguments to every path-carrying tool, which crashes with `Cannot read properties of undefined (reading 'replace')` — cost a false "batch is broken" diagnosis on 2026-11-11).
- **`run_command`'s own argument key is `args`** (an array, spread into the command as separate arguments); `arguments` is only the key INSIDE a batch item. Getting it wrong is silent-ish: `args` missing gives `Cannot read properties of undefined (reading 'command')`, and passing an array where the command wants one object gives `(reading 'arguments')`. Extension-internal commands (ids starting `_`) often take a tree context object rather than plain arguments, e.g. Project Manager's `_projectManager.toggleProjectEnabled` needs `args: [{command: {arguments: [null, "Name"]}}]`.
- Polling after `reload_window` or any delayed effect: a `for` loop with no timer in a Code Mode program spins instantly and proves nothing (it kept answering from the OLD host and looked like "the reload did not happen"). Sleep inside a `batch` (`{sleep: 4000}`) or with the shell's `Start-Sleep`, then read.
- **Speed (vscode-mcp 0.6.x): one phase of a test = one `batch`, with no fixed sleeps, and the assertions inside it.** Write settings -> `wait_config` (the exact key and value) -> `open_file` -> `run_command` -> `wait_for` (the file the program writes, `contains` the marker) -> `expect` (pass/fail for the file the action changed, so the result needs no reading). `run_shell` runs a command in the workspace folder and returns exit code/stdout/stderr, so disk state and exit codes come back inside the batch; never open a terminal or a second PowerShell for it. Assert on a program's effects (files it writes, exit codes) instead of screenshotting the output channel, which cannot be read through the API.
- `expect` compares the open document (unsaved edits included) or the file on disk: `equals`, `contains`, `not_contains` or `matches` (regular expression, no `(?i)` - JS has no inline group; use `[Tt]`), line endings normalised. On failure it returns the first differing line with expected and actual, so only mismatches cost reading. Batch it after every action that changes text.
- An extension that serves HTTP is tested with curl or node through `run_shell`, no browser: status codes with `-w`, headers with `-D file`, and one node script can do HEAD/Range/If-None-Match in a single call. A websocket feature (live reload) is a client script run in the foreground that touches a file itself and collects the messages; extension packages often already ship a client module (`faye-websocket` in Live Server) - require it by absolute path.
- Put a marker character in test text to mark the cursor and compute line/column from it; compare the file text after the action with an expected string exactly, normalising line endings (new files in this editor are CRLF; only compare CRLF deliberately).
- Completions, snippets, hover, definition: `complete` (path, line, character, optional `filter`, `limit`), `hover`, `definitions`. `run_command vscode.executeCompletionItemProvider` is capped at 20,000 characters and a JS/TS file returns every global.
- Features triggered by typing (Enter indentation, comment generators such as `/**` + Enter): place the cursor with `open_file`, then `run_command type` with `[{"text": "\n"}]`. Extension commands bound to a key (such as `pythonIndent.newlineAndIndent`) can be run directly.
- Snippet bodies: `editor.action.insertSnippet` with `[{"snippet": "..."}]` or `{"name": "...", "langId": "..."}`.
- Diagnostics: `get_diagnostics` (optionally `source`). Another extension's output or log: `read_log` (pattern). Formatting and transform commands: `run_command` then `get_text`.
- **Only call commands the extension actually contributes.** `package.json` `contributes.commands` is the palette surface; the bundle usually registers more, and those internal ids can no-op or do something destructive when invoked without the arguments their code action passes (markdownlint's `fixLine` deletes the line given a made-up `fixInfo`). Check `contributes.commands` first, or run the id and read the result, never both at once with fixtures you want to keep.
- **`pending: true` with `dialogs: []` means a quick pick or input box, not a native modal** — and it is DRIVABLE. The 12 s dispatch guard reports the native dialog list it can see; a workbench quick pick is invisible to every API, so an empty list is the diagnosis. Do not record the feature as a gap: chain `workbench.action.quickOpenSelectNext` (move the selection) and `workbench.action.acceptSelectedQuickOpenItem` (accept) with ~0.6-0.8 s sleeps between steps, and multi-step wizards work too (codezombiech.gitignore, 2026-11-12: template pick, then Append/Overwrite pick, verified by the .gitignore content each time). `workbench.action.closeQuickOpen` abandons a pick you cannot proceed with.
- **A pick's LIST is driven by those commands; a pick's TEXT needs the OS input primitives, and the procedure is yours to run:**
  1. `activate_window({title:"<window subtitle>"})` and read `ok`. `ok:false` means nothing moved.
  2. If it refused, the window is behind another app: `click_at` a point that belongs to it (from its bounds, e.g. a strip not covered by the front window) — a real click activates it — then `activate_window` again and check `ok`.
  3. Only with `ok:true`: `send_keys({text:"myproj"})`, then `run_command workbench.action.acceptSelectedQuickOpenItem`.
  **Never call `send_keys` on a refused activation**: it goes to whatever has the focus. 2026-11-14 an unguarded send typed a stray "7" into the user's own editor, which is the whole reason the gate is written down here and not built into the tool. `run_command type` reaches the active editor only, never a quick input.
- **A toast action:** `notifications.focusLastToast` then `send_keys({keys:["tab","enter"]})`. It did NOT land 2026-11-14 while a second toast (a Copilot one) was on screen — focus went to the wrong toast. Clear other toasts first; if the keys still do not land, fall back to `click_at` with a coordinate read from the toast's own bounding box, never blind into the status-bar region.
- **`click_at({x,y,button,count})` clicks absolute screen pixels** through the OS input queue: no focus change, no window logic. Get the coordinate from a window capture, and give the window origin yourself when the capture was window-relative.
- **`reload_window` is on the default surface and legal as the LAST call of a `batch`** (0.9.2): `batch([..., {tool:"reload_window"}])` returns every result and the host restarts about 0.5 s later; poll `get_help` until `pid` changes (2-4 s), and do not put anything after it in the batch.
- **A language-service extension is tested from five angles** (worked on C/C++, 2026-11-15, and on YAML/markdownlint earlier): `get_diagnostics` for exact verdicts and ranges (copy the code numbers and messages into the row); `complete` at a position where the answer is knowable (`p.` after a struct must return exactly its fields); `hover` / `definitions` / `references` for resolution; `editor.action.formatDocument` + `get_text` for the formatter; and two A/Bs — a setting that silences the feature (`C_Cpp.errorSquiggles: "disabled"`) and a config file that changes the semantics (`c_cpp_properties.json` `defines` making a guarded symbol resolve), each showing the before and after. For a debugger: a `launch.json` config, run to completion, then `stopAtEntry: true` (the program's side effect must NOT happen), `debug.continue` (it must), `debug.stop`.
- A rule-based linter can emit MORE THAN ONE diagnostic on a line (markdownlint reports MD022 twice for a heading - blanks above and blanks below are separate violations), so compare diagnostics as a set of (line, code), not a count.
- **A decoration-only extension (Better Comments, Error Lens, Todo Highlight) IS testable: capture the window and count exact pixels.** Nothing in the API exposes decorations, so configure each tag/scenario with a DISTINCT background colour, put every scenario on its own line of one fixture, capture the window once (PrintWindow with flag 2 into a 32bpp bitmap, then count pixels equal to each configured colour) and read the result per colour: presence or absence, and the bounding box's y range names the line. One colour per scenario means one capture can answer a dozen documentation claims, and the same capture repeated after a setting change is the A/B control (0 px with the feature off proves the pixels come from the extension, not the theme). Bring the window to the front for the capture only if PrintWindow returns an empty frame; never leave it there.
- **First call after installing an extension: `list_commands({filter: "<id prefix>."})`.** If its contributed commands are missing, nothing it documents can be exercised - run_command answers "command not found", quick picks cannot be driven, and a fixture is wasted effort. Reinstall + reload once to rule out a stale install, then record a measured negative and stop (Todo Tree 0.0.226, 2026-11-12: view renders, 0 of 34 commands registered, nothing scanned, no highlights).
- JSON bodies with non-ASCII characters: escape them as `\uXXXX` before posting (Windows PowerShell 5.1 writes the console codepage otherwise). PowerShell 5.1 has no `` `u{e9} `` escape: use `[char]0xE9`.
- Inline decorations, tree views and webviews have no API to read them; prove them with a window capture plus pixel counts (see the decoration bullet), or `click_at` for something that must be operated.
- An extension pack installs its members too: triage the members and record a row for each.

- `run_command` and the generated command tools now answer in about 12 s with `pending: true` plus the native dialogs they can see when a command has not returned (vscode-mcp 0.8.3): a modal is the usual cause, and `dismiss_dialog` is then one call away. Answering it lets the command finish. Do not re-run the command blindly; check the effect first.
- **`editor.action.formatDocument` with more than one formatter registered for the language raises VS Code's native "Configure Default Formatter" dialog** (met with beautify + the built-in JS formatter, 2026-11-12; the user waited minutes on it). Pin the formatter in workspace settings FIRST - `"editor.defaultFormatter": "<extension id>"` - and the dialog never appears. If it does appear anyway, `list_dialogs` + `dismiss_dialog` immediately; never leave it up.

- **An extension pack is NOT always "contributes nothing"** (2026-11-15, `vscjava.vscode-java-pack` 0.31.2): this one contributes 13 commands, 3 settings, a walkthrough, six webview serializers and a custom editor, so the round is a full test plus a member check, not a cpptools-style formality. Its `extensionPack` was exactly the six extensions the install pulled (redhat.java, java-debug, java-test, maven, **gradle**, java-dependency) - read the installed `package.json` first; the graded list said Gradle was separate and it was a member, which changed the queue (a member with no row of its own needs a round).
- **A webview command is verified by its panel title, and two commands can share one panel.** The Java pack's `java.overview`/`java.gettingStarted`/`java.extGuide`/`java.welcome`/`java.installJdk` each produce their own tab ("Java Overview", "Tips for Beginners", "Java Extensions Guide", "Java Help Center", "Install New JDK"), while `java.projectSettings`, `java.runtime` and `java.classpathConfiguration` all reveal ONE "Project Settings" panel on a different page - the page is only visible in a window capture (`java.runtime` showed the JDK Runtime tab with the JDK 25.0.4.1 path), so capture when the distinction is the point. `java.welcome.fromWalkthrough` opens a *second* "Java Help Center" panel in the side group.
- **Startup views are gated on the extension's own globalState, not its settings** (2026-11-15): `java.help.firstView: "welcome"` plus a reload plus opening a Java file opened nothing, because `activate()` only schedules the first view when the `showWhenUsingJava` global state key is set. Test the command directly and cite the gate; do not call the setting broken.
- **A custom editor's tab vanishing IS the extension's error signal** (2026-11-15): `java.formatterSettings` opened no tab and toasted "The current profile is invalid, please check it in the Settings and try again." because the pack's `parseProfile` only accepts `<profile kind="CodeFormatterProfile">` (`CodeFormatterOptions` is rejected). With a valid profile the custom editor opened and rendered "Java Formatter Settings" with a live preview. Check the extension's own toast/notification before blaming `vscode.openWith`: that command does open a tab with `'default'` as the view id, which proves the harness path works.
- **`get_active_file` cannot tell a custom editor from a text editor** over the same file - it always returns the text document - so the proof that `java.formatterSettings.showTextEditor` switched editor types came from the editor-switcher label in a window capture ("Java Formatter Settings Editor" before, "Text Editor" after), not from the API.

- **A Gradle extension is testable with no `gradle` on PATH** (2026-11-15, `vscjava.vscode-gradle` 3.19.0): expand a distribution to a tools folder (Gradle 9.2.0 kept at `C:\Users\donal\tools\gradle-9.2.0`) and let the fixture carry a wrapper (`gradle wrapper`) - that is what the extension attaches its build to. The tree groups tasks (build / build setup / documentation / help / other / verification); a custom task lives under "other", and DOUBLE-CLICKING it runs it (`gradle.runTaskDoubleClick`): the task terminal shows "> Executing task: gradle: receipt" and "BUILD SUCCESSFUL in 444ms", but the proof is the file the task writes, checked with `run_shell` after the receipt was recycled.
- **`gradle.stopDaemons` raises a native Yes/Cancel box**, not a quick pick: `run_command` answers `pending: true` with the dialog listed, and `dismiss_dialog {"button":"Yes"}` completes it - the Gradle Daemons view then reads "No Gradle Daemons".

- **A server extension is tested from outside with `run_shell` + curl, and `reload_window` is the reset button** (2026-11-18, `ms-vscode.live-server`). `run_shell` runs in the workspace folder, so `curl -s -o NUL -w "root:%{http_code}" http://127.0.0.1:3000/` reports status without opening a terminal; `curl -s -D - -o NUL <url>` dumps headers (where a configured `httpHeaders` shows up); a directory listing's own hrefs are worth fetching too (`%5Cliveprobe/` answered 200 — the backslash is normalised, so do not call it broken on sight). Two things that ruin a server A/B: a `start` after an `end` can leave the old instance bound when the extension has not released it (check `netstat -ano | grep LISTENING` before believing a 404), and an extension may serve *unsaved editor buffers*, so a "the server shows old content" verdict needs the `dirty` flag from `get_open_files` read in the same batch — live-server served the edited buffer (`dirty:true`) while the disk file still held v1.
- **Windows quoting, not curl, breaks `run_shell` commands** (2026-11-18): `curl … \"http://…\"` (escaped quotes inside a JSON string) fails with exit 3 and `-w` reporting `000`, and `findstr /C:"X-Audit-Probe"` is read as two arguments ("Cannot open Accept-Ranges"). The UIA tree exposes the terminal only as a `textfield` with canvas images, and `read_log` covers host logs, so the task output looks unreadable - but `workbench.action.terminal.focus` → `workbench.action.terminal.selectAll` → `workbench.action.terminal.copySelection` puts the whole buffer in the clipboard, and `computer.clipboard.read()` returns it as text: `*  Executing task: Live Preview: Run Server`, `Server already on at http://127.0.0.1:3000/`, `> [11/18/26 11:36:30] GET: /liveprobe/index.html | 200`. No launch.json is involved.
- **Breakpoints outlive the fixtures that created them** (2026-11-18): `debug_state` listed breakpoints on `work/vetur_probe/App.vue:25` and `work/goprobe/calc_test.go:5` from earlier rounds whose folders had already been recycled. `breakpoints` / `clear_breakpoints` (per path) clean them; check the list when a round ends with a debugger, because `get_open_files` and `list_extensions` both say nothing about them.
- **An empty hover is usually a grammar with no documentation, not a broken provider** (2026-11-18, `redhat.vscode-xml`). `hover` on `<entry>` returned 0 matches while the XSD had no `xs:documentation`; adding `<xs:annotation><xs:documentation>…</xs:documentation></xs:annotation>` made the same position answer "…plus Source: catalog.xsd". Also read the raw API: `vscode.executeHoverProvider` serialises a MarkupContent as `{}` in the bridge's JSON while the bridge's own `hover` tool renders it as text — so `contents:[{}]` is "a hover exists with content the raw route cannot show", never "no hover". Only when both routes and a documented grammar still answer nothing is it a defect (DTD hover was filed as redhat-developer/vscode-xml#1195).
- **`executeCodeActionProvider` answers for the cursor's line, not for the file** (2026-11-18): at the XML declaration (line 0) a grammar-less XML returned only "Minify XML" and Copilot's actions; moved inside the body (line 1) the same file returned the whole generator set ("Generate 'plain.xsd' and bind with xsi:noNamespaceSchemaLocation", … "Generate 'plain.rng' and bind with RelaxNG") plus "Bind to existing grammar/schema". Those entries carry no `command` or `edit` in the JSON, so the action can be seen but not applied through the bridge without the quick-fix UI.
- **Read a contributed setting's schema before blaming the feature** (2026-11-18): `xml.colors` entries need `expressions: [{ "xpath": "fill/@color" }]` — objects with an `xpath` key. With bare strings the array is accepted silently and the colour provider answers `[]`; with the objects it returns `{range 3:15-3:22, color rgb(0.2,0.4,0.8)}`. `package.json`'s `items.properties` says this in one line.

The first pass recorded that saving a fixed `books.rng` cleared the grammar's own diagnostics while the bound XML kept "There are '2' errors in 'books.rng'." and `Index 0 out of bounds for length 0` until `XML: Restart Language Server`. A retest the same day on the same 0.29.3 did not reproduce it. In each case the XML went from those two errors to `element "book" not allowed anywhere; expected element "books"`. The Java string is the message for a grammar that has no `<start>`, not a stuck server.
- **The code-action widget wants `acceptSelectedCodeAction`, and a `send_keys` Enter goes wherever the foreground is** (2026-11-18): `editor.action.quickFix` opens a list whose first entry is already focused, and `acceptSelectedSuggestion` (the suggestions widget's command) does nothing there — `acceptSelectedCodeAction` applied the XML schema generator, which wrote `plain.xsd` and rewrote the document's root with the `xsi` binding in one step. - **A debugger round starts by listing the toolchains, not by assuming** (2026-11-18, `vadimcn.vscode-lldb`): the first pass went looking for a debuggee in Go because "no C compiler is installed" was taken for granted; `Get-Command clang,gcc,rustc,zig` found MinGW-w64 gcc 16.1.0, rustc, cmake and ninja already on PATH. - **Breakpoint verification is answered by DAP `setBreakpoints`, and it is the difference between "the adapter is broken" and "this binary has no line tables"** (2026-11-18): against the Go build every entry came back `{"message":"Resolved locations: 0","verified":false}` (source lines *and* `main.add`), while the C build answered `{"line":5,"message":"Resolved locations: 1","verified":true}` and then stopped there with the stack `add:5 → main:12 → __tmainCRTStartup:184`. - **`evaluate` has two personalities** (2026-11-18, CodeLLDB): with `context: "watch"` it evaluates ("a + b" → `{"result":"1","type":"long long"}`), while `context: "repl"` feeds the LLDB command line, where a plain expression answers `error: ambiguous command 'a'. Possible matches: apropos, add-dsym, attach` and `p a + b` answers an empty result. Ask the watch context when the question is "what is this value".
- **`pause` needs a `threadId` and `threads` only answers while stopped** (2026-11-18): `debug_request {request:"pause"}` alone answers `Malformed message`; `{request:"pause",args:{threadId:0}}` pauses, after which `threads` returns real ids (`1: tid=4176 …`). - **`lldb.selfTest` raises a modal, and an unanswered modal makes every later call look hung** (2026-11-18): the dialog's text is "CodeLLDB self-test completed successfuly." ## What `redhat-developer` actually tests (READMEs of all 288 repos, 2026-11-18)

The account is `redhat-developer`. Every README was read. Most repos are product, operators, quickstarts, or docs and describe no test method. The ones that do, and what they change here:

**This audit's framework is `vscode-extension-tester`, plus `vscode-extension-tester-example`.** The example has one file per surface (activity bar, bottom bar, commands, extensions view, input, menus, modal, notifications, settings, status bar, text editor, tree, webview). `npm run ui-test` is `extest setup-and-run`. A failed test takes a screenshot. `vscode-server-connector` runs the same harness as `npm run public-ui-test`. `intellij-common-ui-test-library` is the IntelliJ twin: `UITestRunner.runIde` returns a Remote-Robot, tests live in `src/it`, `closeIde` in the teardown.

**A language round follows `vscode-java`'s `test/Test Plan.md`.** Wait until the server is up (status bar) before counting problems. The oracle is a known project and a known count: two errors, one snippet, one error, one code action, zero. Eclipse, Maven, multimodule, Gradle, and a single file are separate cases.

**A failure is kept, not cleaned up first.** `rhdh-test-instance` runs Playwright smoke and does not tear the instance down when a check fails. Traces stay in `e2e/results/`. ExTester screenshots every failed test, named by the test title. `AITestTriage` exists only because those JUnit files and screenshots are still there. Do not uninstall and recycle before the failing evidence is in the row.

**The instance under test is not the user's.** `podman-desktop-hummingbird-ext` uses an isolated profile, a locally built artifact, and a pinned host binary. ExTester's locale guide says the same: install the language pack into the test instance, do not use a different `code` on PATH. **Webview frame switch, from `WebviewMixin.ts`.** `switchToFrame` defaults to 5000 ms. **ExTester example tests, from `src/ui-test/*.test.ts` and the page-object source (2026-11-18).** Mocha default timeout is 5 seconds. The example raises `before` to 8–30 seconds. `wait()` is element visible, 5 seconds. Copy these, not the README:

- Problems: open the view, sleep 3 seconds after opening the file, then `driver.wait` up to 15 seconds until `getAllVisibleMarkers` is non-empty.
